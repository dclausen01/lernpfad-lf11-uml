  - frage: "Bei einer Komposition Rechnung – Rechnungsposition steht an der Rechnung „1..*“. Was ist falsch?"

    richtig_text: Richtig. Ein Teil kann nicht zu mehreren Ganzen gleichzeitig gehören.

    richtig_text: Genau. Tätigkeiten gehören ins Aktivitätsdiagramm oder als do-/Aktion in den Zustand.
    falsch_text: Ein Zustand beschreibt, wie etwas ist – nicht, was getan wird.

    richtig_text: Richtig. Antworten sind gestrichelt.
    falsch_text: Antworten (Rückgaben) zeichnest du gestrichelt mit offener Spitze. Sie dürfen weggelassen werden, wenn nichts zurückkommt – aber nie durchgezogen.

## 1. Die Klassiker im Klassendiagramm

:::screenshot material/p2-fehler-raute.svg
Links falsch: Die Raute der Komposition sitzt an der Rechnungsposition, an der Rechnung steht 1..*. Rechts richtig: Die gefüllte Raute sitzt an der Rechnung (dem Ganzen), dort steht 1, an der Rechnungsposition 1..*.
:::

| Fehler | So ist es richtig |
| --- | --- |
| Raute am Teil | Raute **am Ganzen** |
| Komposition mit `*` am Ganzen | am Ganzen nur `1` oder `0..1` |
| Vererbungspfeil zeigt zur Unterklasse | Dreieck an der **Oberklasse** |
| Interface mit durchgezogener Linie umgesetzt | Realisierung **gestrichelt** |
| `- String name` (Java-Reihenfolge) | `- name : String` |
| Multiplizität nur an einer Seite | an **beiden** Enden |
| Beziehung **und** gleiches Attribut | entweder Linie (mit Rollennamen) oder Attribut |
| Klassenname im Plural („Kunden“) | Singular („Kunde“) |
| statisch kursiv, abstrakt unterstrichen | **statisch unterstrichen, abstrakt kursiv** |

## 2. Die Klassiker im Anwendungsfalldiagramm

:::screenshot material/p2-fehler-usecase.svg
Oben richtig: Der Kunde ist mit „Artikel suchen“ und „Bestellung aufgeben“ verbunden, „Bestellung aufgeben“ inkludiert „Bezahlen“. Unten falsch: Einloggen, Artikel suchen und Bezahlen sind mit Pfeilen zu einem Ablauf verkettet.
:::

| Fehler | So ist es richtig |
| --- | --- |
| Anwendungsfälle als Ablaufkette | jeder Fall einzeln am Akteur; Ablauf → Aktivitätsdiagramm |
| «extend»-Pfeil zeigt zum Erweiterer | vom Erweiterer **zum Basisfall** |
| «includes» / «extends» | **«include» / «extend»** |
| Akteur innerhalb der Systemgrenze | Akteure stehen **außerhalb** |
| konkrete Person als Akteur („Frau Meier“) | Rolle („Sachbearbeiter:in“) |
| Anwendungsfall als Substantiv („Bestellung“) | Verb-Phrase („Bestellung aufgeben“) |

## 3. Die Klassiker in Aktivitäts-, Sequenz- und Zustandsdiagramm

| Diagramm | Fehler | So ist es richtig |
| --- | --- | --- |
| Aktivität | Bedingung in der Raute („verfügbar?“), ohne Guards | Guards in `[ ]` an den **ausgehenden** Kanten |
| Aktivität | Guards decken nicht alle Fälle ab | `[sonst]` ergänzen oder `<`/`>=` sauber trennen |
| Aktivität | Raute statt Balken für Parallelität | **Balken** = gleichzeitig, **Raute** = entweder–oder |
| Aktivität | Endknoten in einem parallelen Zweig, der eigentlich nur diesen Zweig beenden soll | **Ablaufende ⊗** |
| Sequenz | Antwort durchgezogen | Antwort **gestrichelt** |
| Sequenz | synchron/asynchron verwechselt | gefüllt = wartet, offen = wartet nicht |
| Sequenz | `alt` ohne Guards oder ohne Trennlinie | `[Bedingung]` je Zweig, gestrichelte Trennlinie |
| Sequenz | neues Objekt steht schon oben | erzeugtes Objekt beginnt **auf Höhe der create-Nachricht** |
| Zustand | Zustand als Tätigkeit („ausleihen“) | als Zustand („ausgeliehen“) |
| Zustand | `[Ereignis] Bedingung / Aktion` vertauscht | `Ereignis [Bedingung] / Aktion` |
| Zustand | Ereignis an der Transition aus dem Anfangszustand | dort höchstens eine Aktion |
| Zustand | Selbsttransition, obwohl entry/exit nicht erneut laufen sollen | **interne Transition** im Zustand |

## 4. Deine Abgabe-Checkliste

:::checkliste Vor dem Abgeben – für jedes Diagramm
- Habe ich das Diagramm gezeichnet, nach dem gefragt war?
- Hat das Diagramm einen Namen (Systemgrenze, Rahmen, Überschrift)?
- Habe ich jede Information aus der Aufgabe untergebracht? (Text noch einmal Satz für Satz abhaken.)
- Stimmen alle Pfeilspitzen und Linienarten (durchgezogen / gestrichelt)?
- Haben alle Verzweigungen und Fragmente Bedingungen in eckigen Klammern?
- Stehen Multiplizitäten an beiden Enden jeder Assoziation?
- Passen die Namen zu den anderen Diagrammen der Aufgabe (Klassen, Methoden, Zustände)?
- Ist alles lesbar – auch für jemanden, der den Aufgabentext nicht kennt?
:::

:::aufgabe basis 10 1 · Fehlerjagd Klassendiagramm
Finde die fünf Fehler in dieser Beschreibung eines Klassendiagramms:

- Klasse `Kunden` mit den Attributen `- String name` und `- adresse : Adresse` sowie einer Linie zur Klasse
  `Adresse`.
- `Girokonto` ist mit `Konto` durch eine durchgezogene Linie verbunden; das hohle Dreieck sitzt an `Girokonto`.
- Komposition `Bestellung` ◆— `Position`, an `Bestellung` steht `1..*`.
- Die abstrakte Methode `berechneZins()` ist unterstrichen.

:::loesung
1. `Kunden` → Singular `Kunde`.
2. `- String name` → `- name : String`.
3. `adresse` ist doppelt modelliert (Attribut **und** Linie) – eins von beiden weglassen.
4. Das Dreieck gehört an die Oberklasse `Konto`, nicht an `Girokonto`.
5. An der Seite des Ganzen (`Bestellung`) darf bei einer Komposition nur `1` (oder `0..1`) stehen.

Bonus: Abstrakte Methoden sind **kursiv**, nicht unterstrichen (unterstrichen = static).
:::
:::

:::aufgabe plus 10 2 · Fehlerjagd Verhalten
Was ist jeweils falsch, und wie wäre es richtig?
1. Aktivitätsdiagramm: Eine Raute trägt die Aufschrift „Betrag > 100?“, die beiden Kanten sind mit „ja“ und
   „nein“ beschriftet.
2. Sequenzdiagramm: `:App` ruft `speichern()` an `:Datenbank` auf und wartet auf das Ergebnis. Der Pfeil hat
   eine offene Spitze.
3. Zustandsdiagramm: Die Transition vom Zustand „offen“ nach „bezahlt“ ist mit `[zahlungEingegangen] / Beleg
   drucken` beschriftet. `zahlungEingegangen` ist ein Ereignis.
4. Zustandsdiagramm: Der Zustand „in Prüfung“ hat keine ausgehende Transition und ist kein Endzustand.

:::loesung
1. In UML gehören die Bedingungen als Guards an die Kanten: `[betrag > 100]` und `[sonst]`. (Ein Text an der
   Raute ist als Notiz erlaubt, ersetzt aber die Guards nicht.)
2. Wer wartet, schickt eine **synchrone** Nachricht – gefüllte Pfeilspitze. Dazu gehört eine gestrichelte
   Antwort.
3. Ereignisse stehen **ohne** Klammern vorne: `zahlungEingegangen / Beleg drucken`. In eckige Klammern gehören nur
   Bedingungen.
4. Das Objekt bliebe für immer „in Prüfung“. Es fehlt eine Transition (z. B. `pruefungAbgeschlossen`) – oder der
   Zustand ist überflüssig.
:::
:::
