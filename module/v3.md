## 1. Die Elemente

Das Sequenzdiagramm zeigt, **welche Objekte sich in welcher Reihenfolge Nachrichten schicken**. Die Zeit läuft
von oben nach unten. Es ist das wichtigste Interaktionsdiagramm und passt gut, wenn du einen Methodenaufruf, eine
Anmeldung oder die Kommunikation zwischen App und Server erklären willst.

:::screenshot material/v3-elemente.svg
Grundelemente: Lebenslinien :A, :B und :C, Aktivierungsbalken, eine synchrone Nachricht mit Antwort, eine asynchrone Nachricht, ein Selbstaufruf, die Erzeugung von :C mit «create» und die Zerstörung von :C (X am Ende der Lebenslinie).
:::

| Element | Darstellung | Bedeutung |
| --- | --- | --- |
| Lebenslinie | Rechteck `name : Klasse` + gestrichelte senkrechte Linie | ein beteiligtes Objekt; `: Klasse` heißt „irgendein Objekt dieser Klasse“ |
| Akteur | Strichmännchen mit Lebenslinie | ein Mensch oder externes System, das von außen auslöst |
| Aktivierung | schmaler Balken auf der Lebenslinie | das Objekt arbeitet gerade (eine Methode läuft) |
| synchrone Nachricht | durchgezogen, **gefüllte** Spitze | Methodenaufruf; der Sender **wartet** |
| asynchrone Nachricht | durchgezogen, **offene** Spitze | Signal; der Sender **wartet nicht** |
| Antwort | **gestrichelt**, offene Spitze | Rückgabe an den Aufrufer |
| Erzeugung | **gestrichelt**, offene Spitze, auf den **Kopf** des neuen Objekts | `new` – das Objekt beginnt erst hier |
| Zerstörung | X am Ende der Lebenslinie | das Objekt wird gelöscht |
| Selbstaufruf | Pfeil zurück auf die eigene Lebenslinie | das Objekt ruft eine eigene Methode auf |

:::notiz Schreibweise in der Prüfung
- Die **Erzeugungsnachricht** ist gestrichelt mit offener Spitze und mit `create` beschriftet – so steht es in der
  UML-Norm und im Notationsblatt des Prüfungskatalogs. Manche Lehrbücher zeichnen sie durchgezogen.
- **Aktivierungsbalken** sind optional. Wenn du sie zeichnest, dann vollständig: vom Aufruf bis zur Antwort.
- Antworten dürfen weggelassen werden, wenn nichts zurückgegeben wird. An die Antwort schreibst du den
  Rückgabewert oder die Variable, in der er landet.
:::

## 2. Kombinierte Fragmente

Bedingungen und Schleifen zeichnest du als **Rahmen** um die betroffenen Nachrichten. Links oben steht der
Operator, die Bedingung (Guard) steht in eckigen Klammern.

| Operator | Bedeutung | Entspricht im Code |
| --- | --- | --- |
| `alt` | Alternativen, durch gestrichelte Linien getrennt – genau eine wird ausgeführt; der letzte Zweig heißt meist `[else]` | `if … else if … else` |
| `opt` | wird ausgeführt oder nicht | `if` ohne `else` |
| `loop` | Wiederholung: `loop [Bedingung]`, `loop(10)` für genau 10-mal oder `loop(min,max) [Bedingung]` | `while`, `for` |
| `par` | parallele Abschnitte | Threads |
| `break` | Abbruch: Fragment ausführen, dann den umgebenden Ablauf verlassen | `break` / `return` |

:::screenshot material/v3-ausleihe.svg
Sequenzdiagramm „Rad ausleihen“: Der Kunde ruft in der App radAusleihen(radId) auf. Die App ruft synchron ausleihen(kundeId, radId) am Ausleihservice auf, der seine Verfügbarkeit per Selbstaufruf prüft. Im alt-Fragment [verfuegbar] erzeugt der Ausleihservice ein Objekt a:Ausleihe, schickt asynchron oeffnen() an das Schloss und antwortet der App mit a. Im Zweig [else] antwortet er mit null, und die App meldet „Rad nicht verfügbar“.
:::

:::achtung Typische Fehler
- Antwort mit durchgezogener Linie gezeichnet – Antworten sind **immer gestrichelt**.
- Synchron und asynchron verwechselt. Frag dich: Wartet der Sender auf ein Ergebnis?
- Guards ohne eckige Klammern oder bei `alt` vergessen, die Zweige mit einer gestrichelten Linie zu trennen.
- Aktivierungsbalken enden, bevor die Antwort zurück ist.
:::

## 3. Vom Code zum Sequenzdiagramm

Eine sehr typische AP2-Aufgabe: „Erstellen Sie zu der Methode `abrechnen` ein Sequenzdiagramm.“

```java
public class Kasse {
    private Drucker drucker;

    public double abrechnen(Warenkorb wk) {
        double summe = wk.summe();
        Beleg b = new Beleg(summe);
        drucker.drucke(b);          // asynchron: die Kasse wartet nicht
        return summe;
    }
}

public class Warenkorb {
    private List<Position> positionen;

    public double summe() {
        double s = 0;
        for (Position p : positionen) {
            s += p.preis();
        }
        return s;
    }
}
```

:::schritte
1. Lege die Lebenslinien fest: Wer ruft auf (hier ein Akteur „Kassierer“), welche Objekte sind beteiligt
   (Kasse, Warenkorb, Position, Drucker, Beleg)?
2. Gehe den Code **Zeile für Zeile** durch. Jeder Methodenaufruf auf einem anderen Objekt wird ein Pfeil.
3. `return` wird zur gestrichelten Antwort. `new` wird zur Erzeugungsnachricht auf den Kopf des neuen Objekts.
4. Die `for`-Schleife wird ein `loop`-Fragment, ein `if` ein `opt`- oder `alt`-Fragment.
:::

:::screenshot material/v3-kasse.svg
Sequenzdiagramm zur Methode abrechnen: Der Kassierer ruft abrechnen(wk) an der Kasse auf. Die Kasse ruft summe() am Warenkorb auf, der in einem loop-Fragment [für jede Position p] preis() an der Position aufruft. Danach erzeugt die Kasse b:Beleg mit «create», schickt drucke(b) asynchron an den Drucker und antwortet mit der Summe.
:::

:::aufgabe basis 15 1 · Login mit drei Versuchen
Zeichne ein Sequenzdiagramm: Ein **Benutzer** gibt Name und Passwort im **Onlineportal** ein. Das Portal lässt
die Daten von der **Datenbank** prüfen und bekommt ein Ergebnis zurück. Ist es in Ordnung, meldet das Portal
„Anmeldung erfolgreich“. Sonst meldet es „Daten falsch“, und der Benutzer darf es erneut versuchen – insgesamt
höchstens dreimal. Nach dem dritten Fehlversuch meldet das Portal „Konto gesperrt“.

:::checkliste Selbstcheck
- Ein `loop`-Fragment mit Höchstzahl und Bedingung.
- Darin ein `alt`-Fragment mit drei Zweigen und Guards.
- Alle Antworten gestrichelt.
:::

:::loesung
:::screenshot material/v3-login.svg
Lösung: loop(1,3) [nicht angemeldet] um den Ablauf login(name, pw) vom Benutzer an das Onlineportal und pruefe(name, pw) vom Portal an die Datenbank mit der Antwort ergebnis. Darin ein alt-Fragment mit den Zweigen [ergebnis = ok] „Anmeldung erfolgreich“, [versuche < 3] „Daten falsch“ und [else] „Konto gesperrt“.
:::
Achte auf die Logik der Bedingung: Die Schleife läuft, solange der Benutzer **nicht** angemeldet ist **und**
noch Versuche übrig sind – die Höchstzahl regelt `loop(1,3)`. Ein „oder“ an dieser Stelle wäre falsch, weil die
Schleife dann nach einer erfolgreichen Anmeldung weiterliefe.
:::
:::

:::aufgabe plus 15 2 · Passwort zurücksetzen
Ein **Benutzer** klickt im **Portal** auf „Passwort vergessen“ und gibt seine E-Mail-Adresse an. Das Portal
fragt die **Benutzerverwaltung**, ob es einen Benutzer mit dieser Adresse gibt, und wartet auf die Antwort. Nur
wenn es ihn gibt, erzeugt das Portal ein Objekt `t:Token` und lässt den **Mailserver** einen Link verschicken –
ohne auf den Versand zu warten. In jedem Fall antwortet das Portal: „Falls die Adresse existiert, wurde ein Link
gesendet.“

:::loesung
:::screenshot material/v3-passwort.svg
Lösung: Der Benutzer ruft passwortVergessen(email) am Portal auf. Das Portal ruft synchron finde(email) an der Benutzerverwaltung auf und erhält benutzer zurück. Im opt-Fragment [benutzer != null] erzeugt das Portal t:Token mit «create» und schickt asynchron sendeLink(email, t) an den Mailserver. Danach antwortet das Portal dem Benutzer.
:::
- `opt` statt `alt`, weil es nur einen bedingten Zweig gibt.
- Der Versand ist **asynchron** (offene Spitze, keine Antwort) – das Portal wartet nicht.
- Die Antwort an den Benutzer verrät absichtlich nicht, ob die Adresse existiert. Das ist eine bewusste
  Sicherheitsentscheidung, die dir im Diagramm auffallen darf.
:::
:::
